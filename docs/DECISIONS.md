# CarbonFlow — Architectural Decision Records (ADR)

## ADR-001: Deterministic Decimal Arithmetic over Floating Point
- **Context**: Greenhouse gas accounting data is subjected to rigorous third-party financial and sustainability assurance (ISAE 3410). IEEE 754 floating point arithmetic introduces binary rounding errors.
- **Decision**: All calculations use high-precision decimal arithmetic (Java `BigDecimal` standard, implemented via `Decimal.js` in TypeScript runtime).
- **Consequences**: Internal scale is fixed at 8 decimal places with `ROUND_HALF_UP`. Tonnes $CO_2e$ are reported to 4 decimal places. Calculations are 100% reproducible.

---

## ADR-002: Scope 2 Dual-Reporting Model
- **Context**: Under GHG Protocol Corporate Standard (Scope 2 Guidance), companies must report both Location-based (grid average) and Market-based (contractual instruments) emissions.
- **Decision**: Location and Market emission records are maintained as distinct line items. The system strictly forbids summing them ($Location + Market \neq Total$). If market-based factors are unavailable, the record is flagged explicitly rather than copying location data.
- **Consequences**: Executive dashboards and reports display Dual Metrics side-by-side.

## ADR-003: Versioned Emission Factor Immutability
- **Context**: Emission factor updates (e.g. annual eGRID or DEFRA releases) must not silently alter historical carbon inventory reports that have already been audited or reported to regulatory bodies.
- **Decision**: Emission factors are versioned. Each calculation links to a specific immutable `factor_version_id`.
- **Consequences**: Updating a factor creates a new version. Existing calculations and inventory snapshots retain historical factor values.

## ADR-004: Strict Tenant Context Derivation
- **Context**: In multi-tenant SaaS, trusting client-provided headers such as `X-Organization-Id` enables tenancy spoofing if an attacker tampers with headers.
- **Decision**: The backend derives organization identity exclusively from cryptographically verified user tokens and active memberships in `organization_memberships`. All DB queries enforce `WHERE organization_id = :tenantId`.
- **Consequences**: Complete tenant isolation. Cross-tenant access fails with 403 Forbidden.

---

## ADR-005: 8-State Governed Audit State Machine
- **Context**: Moving unverified carbon accounting data directly into reports creates regulatory and assurance risk.
- **Decision**: Implement an 8-state governed workflow (`DRAFT`, `SUBMITTED`, `DATA_COLLECTION`, `VALIDATION`, `REVIEW`, `APPROVED`, `AUDIT_READY`, `LOCKED`) with mandatory checklist validation before approval and locking.
- **Consequences**: Enforces segregation of duties between data owners, accountants, sustainability managers, and reviewers.

## ADR-006: TASK-004A-PREP PostgreSQL Identity Compatibility Decision
- **Status**: ACCEPTED for identity compatibility; TASK-004A persistence remains blocked by refresh-token schema alignment.
- **Context**: The active Node seed data uses arbitrary string identifiers such as `org-tenant-a-1111`, `user-acme-admin-1`, and `mem-a-1`, and stores membership roles as `RoleName` strings. PostgreSQL 18.6 was authenticated at `localhost:5432/carbonflow_dev`, and the exact V1/V2 files were directly applied to the disposable database. Actual V1 inspection confirmed UUID primary and foreign keys, including `organization_memberships.role_id -> roles.id`; actual V2 inspection confirmed nine UUID-backed role records but no organizations, users, permissions, memberships, or refresh tokens. The current V1 `refresh_tokens` table contains only `id`, `user_id`, `token_hash`, `expires_at`, `revoked_at`, and `created_at`, while the active TASK-003 record also requires organization, role, family, and replacement metadata.
- **Decision**: Choose **Option A — map existing development identities to UUID-backed PostgreSQL records while preserving semantic identities**. Resolve development users by their stable semantic identity (for example, email), organizations by an agreed stable business key, and membership roles by the unique `roles.name`; never attempt to insert development string IDs into UUID columns and do not add a legacy mapping table. PostgreSQL UUIDs become the persistence-layer identities while existing Node semantic identity and authorization behavior remain unchanged until a later implementation task explicitly replaces them.
- **Alternatives rejected**:
  1. **Option B — replace all development seed identifiers with UUIDs**: rejected as broader and riskier because it changes fixtures and many dependent references without helping refresh-token persistence.
  2. **Option C — explicit legacy-to-UUID mapping layer**: rejected as unnecessary for development-only identities because stable semantic keys already exist and the PostgreSQL schema supplies the canonical UUID records.
  3. **Option D**: no repository evidence requires a different identity strategy.
- **Preservation requirements**: Every lookup must preserve active user and membership checks, tenant membership, role authorization, TASK-001 tenant/role switching, the TASK-002 authentication boundary, and TASK-003 refresh authorization. Role strings must be translated through the canonical PostgreSQL role relation, never accepted as arbitrary database role IDs.
- **Consequences**: TASK-003 remains unchanged and memory-backed. TASK-004A-SCHEMA-PREP defines the missing persistence relationships in ADR-007; no `V3` was created in TASK-004A-PREP.

## ADR-007: Refresh-Token Persistence Schema Alignment
- **Status**: ACCEPTED and implemented; TASK-004A cleanup completed. PostgreSQL is the sole production refresh-token source of truth.
- **Context**: The actual V1 `refresh_tokens` table stores only token ID, user, hash, expiry, revocation, and creation time. TASK-003 additionally binds every token to an organization, role, family, and replacement. V3 and the PostgreSQL repository now implement those requirements.
- **Decision**: Extend `refresh_tokens` with non-null `organization_id UUID`, non-null `role_id UUID`, non-null `family_id UUID`, and nullable self-referencing `replaced_by_token_id UUID`. Resolve role authorization by joining the recorded user and organization to an active membership whose `role_id` equals the token's recorded role. Keep the family UUID directly on token rows; do not add a family table. Use `ON DELETE CASCADE` for organization, `ON DELETE RESTRICT` for role, and `ON DELETE SET NULL` for replacement. Retain unique token hashes.
- **Authorization alternatives**:
  1. `organization_id + role_id` — selected. It preserves the issued tenant and role even if a membership's role later changes; the active membership is still checked on every refresh.
  2. `membership_id` — rejected as the sole context because mutable membership role data would not preserve the role bound at issuance.
  3. `membership_id + role snapshot` — rejected as redundant for the current model.
- **Rotation decision**: Lock the presented token by unique hash using `SELECT ... FOR UPDATE`; validate expiry, revocation/replacement, active user, and exact active membership; insert the successor; revoke and link the predecessor; commit before responding. A concurrent second request waits and then observes the committed replacement/revocation and is rejected as replay.
- **Constraints and indexes**: Add foreign keys for organization, role, and replacement; unique non-null replacement; non-self replacement check; replacement-implies-revoked check; and an index on `family_id`. No raw token, family table, or speculative expiry index is allowed.
- **Logout decision**: Resolve the presented token's family and update every non-revoked family row in one transaction. PostgreSQL persistence must preserve valid, revoked, rotated, replacement, and family-revocation state across Node restarts.
- **Migration decision**: V1 and V2 remain unchanged. A future `V3__refresh_token_persistence_alignment.sql` must fail closed if token rows exist without a reviewed backfill plan. The current zero-row target needs no data backfill, but emptiness is a verified precondition rather than the design's safety mechanism.
- **Consequences**: V3, the repository, restart/concurrency tests, and legacy cleanup are complete. PostgreSQL is the sole production refresh-token source; no memory fallback remains.

## ADR-008: Calculation and Emission Snapshot Persistence
- **Status**: ACCEPTED and implemented in TASK 2.5.
- **Context**: Calculation results are accounting evidence. Factor versions, GWP values, unit normalization, and Scope 2 dual-reporting semantics must remain reproducible even when reference data changes later. The established engine has no methodology input or methodology version field.
- **Decision**: Keep `server/calc.ts` as the sole formula authority. Production routes resolve factor versions and GWP sets from PostgreSQL, then `calculation-repository.ts` persists the calculation, gas results, emission record, prior active-emission supersession, and activity status in one transaction. V6 adds snapshot columns for factor ID/unit/source/version, GWP name, and conversion factor plus composite tenant foreign keys.
- **Consequences**: Historical calculations retain their original factor/version/GWP snapshot and do not depend on a later active factor. Recalculation creates a new immutable calculation and supersedes prior active emission records without double counting. Scope 2 location and market records remain distinct. No methodology field was invented.

## ADR-009: Plain JDBC (Spring JDBC) as the Java Persistence Technology
- **Status**: ACCEPTED (Phase 2 — Foundation & Decisions; decided with stakeholder sign-off).
- **Context**: The Java backend (`backend-java/`) had no persistence layer at all — an in-memory `ConcurrentHashMap` store. The specification requires evaluating requirements before introducing any ORM. The PostgreSQL schema (V1–V6, 37 tables) is hand-tuned: composite tenant foreign keys (V5/V6), tenant-scoped unique indexes, CHECK constraints, `NUMERIC` precision, and `SELECT … FOR UPDATE` row locks. The active Node reference backend uses raw parameterized SQL with mandatory `WHERE organization_id = $1` predicates.
- **Decision**: Adopt `spring-boot-starter-jdbc` with explicit SQL through `JdbcTemplate`, PostgreSQL as the single source of truth, and Flyway for migrations. No ORM (JPA/Hibernate) or second persistence abstraction is introduced. Repository classes arrive in Phase 3; when they do, every query must carry the tenant predicate and reuse the proven SQL semantics of `server/*-repository.ts`.
- **Alternatives rejected**:
  1. **Spring Data JPA / Hibernate** — rejected: mapping 37 tables with composite tenant FKs and CHECK constraints invites Hibernate/Flyway divergence (`ddl-auto` must stay off), diverges from the proven reference SQL, and adds an ORM the specification explicitly says must first be justified.
  2. **MyBatis** — rejected: another abstraction without a need the plain API does not cover.
- **Consequences**: Full SQL fidelity and direct reuse of reference queries; more boilerplate (`RowMapper`s) than entities. Introducing an ORM later requires a new ADR.

## ADR-010: Authoritative API Contract and Toolchain Alignment
- **Status**: ACCEPTED (Phase 2).
- **Context**: Two contracts coexisted — the Node backend exposes 39 endpoints (the React frontend is wired to them) while the Java prototype exposes 17 with divergent paths (`/audit-rooms` vs `/audits`, `/factors` vs `/reference/emission-factors`) and no refresh/logout/switch endpoints. `pom.xml` declared Java 17 while the target toolchain and installed JDK are Java 21.
- **Decision**:
  1. **The Node contract is authoritative**: paths, the `{success,data,error:{code,message}}` envelope, 201-on-create, and snake_case error codes are what the Java backend must reproduce. Java endpoints converge module-by-module in Phases 3–7; the frontend is not re-wired until Phase 8.
  2. **`pom.xml` `java.version` raised 17 → 21** to match the non-negotiable target and the verified toolchain (OpenJDK 21.0.12.1, Maven 3.9.16).
  3. **Access-token TTL aligned to 15 minutes** (900000 ms), matching `server/auth.ts`; refresh-token rotation arrives with Phase 3 (Identity & Tenant Core).
- **Consequences**: One contract going forward; `backend-java/README.md` claims of "100% API contract match" are withdrawn as false (17 ≠ 39 endpoints).

## ADR-011: RBAC Source of Truth Is the Code Matrix, Not the Database Tables
- **Status**: ACCEPTED (Phase 2).
- **Context**: The canonical model is 9 roles × 44 permission codes (`server/types.ts`, `server/rbac.ts`, `docs/RBAC.md`, seeded into `roles` by V2). The `permissions` and `role_permissions` tables exist but are seeded empty and queried by no code in either backend — DB-backed RBAC is documented, not implemented. The Java prototype carried a wrong 5-role enum including the forbidden `SUPER_ADMIN` and enforced nothing (zero `@PreAuthorize`).
- **Decision**: Port the matrix verbatim into `com.carbonflow.security` (`Permission` enum = 44 codes, `RolePermissions` = exact per-role sets, canonical 9-role `Role` enum). The JWT filter grants one authority per permission (`PERMISSION_<code>`) plus `ROLE_<role>` on every request — derived from the store's current role, never from token claims. Endpoints declare their required permission via `@PreAuthorize`. Parity is enforced by `RolePermissionsParityTest`, which compares the Java matrix set-for-set against a matrix exported from `server/rbac.ts`. The database tables remain unused until a role-administration feature (Phase 7) needs them; making RBAC DB-driven then requires a new ADR plus seeding.
- **Consequences**: Authorization decisions are interchangeable with the Node backend; the 16 pre-existing Java endpoints are now permission-gated (including the audit transition, which Node leaves ungated).

## ADR-012: Flyway as Migration Runner, Shared Migration Folder, Baseline Strategy
- **Status**: ACCEPTED; **execution verified against a live database on 2026-09-26**: PostgreSQL 18.6 at `localhost:5432/carbonflow_dev` was baselined at version 6 (the manually migrated V1–V6 schema, no `flyway_schema_history`) and V7–V8 applied by the application's own Flyway runner; the hermetic test suite additionally re-applies V1–V8 on embedded PostgreSQL 14.10 on every `mvn verify`.
- **Context**: `db/migration/V1–V6` already follow the Flyway naming convention but no Flyway dependency, configuration, or runner existed anywhere; the schema was applied manually (docs/TASKS.md). Additionally the `carbon_audits.status` CHECK (8 states) disagrees with the application's 10-state audit machine (`docs/AUDIT_WORKFLOW.md`, `server/types.ts`), so persisting `CORRECTION_REQUESTED`/`REJECTED` would fail at the database.
- **Decision**:
  1. Flyway (`flyway-core` + `flyway-database-postgresql`) runs at Java application startup; `spring.flyway.locations=classpath:db/migration`.
  2. The **repository-root `db/migration` folder stays the single source of truth**: `pom.xml` packages it onto the classpath, so Java and any deployment tooling apply identical files.
  3. `baseline-on-migrate=true` with `baseline-version=6`: an empty database applies V1…Vn normally; a database already migrated manually through V6 (no `flyway_schema_history`) is baselined at 6 and receives only newer migrations. A *partially* migrated database must be baselined manually.
  4. **V7** (`V7__audit_status_correction_rejection.sql`) extends `carbon_audits.status` to the full 10-state machine. It locates the legacy constraint by *definition* (not assumed name) before dropping it, then adds `carbon_audits_status_check`.
- **Consequences**: The Java backend owns schema evolution from Phase 2 on. V7 only widens a CHECK — backward-compatible with the Node backend (which still keeps audits in memory), so applying it to a Node-era database changes no Node behavior.

## ADR-013: Authentication and Authorization Hardening Baseline
- **Status**: ACCEPTED (Phase 2 — refresh rotation, logout invalidation, and tenant/role switching were completed in Phase 3 under ADR-014; login lockout remains Phase 9 scope).
- **Context**: Phase 1 recorded five Java CRITICAL findings — plaintext password comparison (`AuthController`), zero authorization, a committed HS256 secret in two places, CORS `*` with credentials, and no persistence — plus unauthenticated self-test access and silent token failures.
- **Decision**:
  1. **BCrypt cost 10** (identical to the Node backend's bcryptjs cost 10) for stored hashes and verification. Unknown-account logins still perform one full BCrypt verification against a precomputed dummy hash so response timing cannot enumerate users.
  2. **Fail-closed JWT configuration**: the signing secret comes only from `CARBONFLOW_JWT_SECRET`; startup fails fast when it is missing, blank, or under 256 bits. No default/committed secret remains.
  3. **CORS** from `CORS_ORIGINS` as an explicit origin allow-list (credentials allowed only for listed origins — never `*`).
  4. **Every `/api/v1/**` route requires authentication**; per-endpoint permissions via `@PreAuthorize` (ADR-011); login and `/api/health` are the only public routes; `GET /api/v1/test-suite/run` is restricted to `platform.tenants.manage`.
  5. **Envelope-complete error handling**: security chain returns `{success:false,error:{code,message}}` for 401/403; a `@ControllerAdvice` maps JSON/validation/type/method/not-found/denied/unexpected failures onto the same envelope, logging full detail server-side only (no stack traces to clients).
  6. **Spring wiring trap fixed**: the in-memory store is `@Component`, not `@Repository`, and `PersistenceExceptionTranslationAutoConfiguration` is excluded — otherwise `spring-boot-starter-jdbc` causes `@Repository` beans to be CGLIB-proxied without constructor invocation, nulling public fields that controllers read directly.
- **Consequences**: Phase 1 CRITICAL #1–#5 are resolved in the Java codebase and covered by 36 tests. Residual items explicitly deferred: `?token=` query-string acceptance (log/history leak), no login throttling, demo seed credentials, refresh tokens, DB TLS — tracked for Phases 3, 9, and 10.

## ADR-014: Identity and Tenant Core — JDBC Identity, Refresh Rotation, Registration Lifecycle
- **Status**: ACCEPTED (Phase 3).
- **Context**: Phase 3 had to move authentication off the in-memory store while keeping the Node reference backend's observable contract byte-for-byte where it exists (ADR-010), and to add the pieces neither backend had: a registration/approval flow (API.md documents no users or platform endpoints — greenfield), an organization lifecycle status, and tenant user administration. Two Node gaps had to be corrected deliberately: refresh-token reuse detection revokes nothing (`server/postgres-refresh-repository.ts` reports `REFRESH_TOKEN_REVOKED` but leaves the replacement alive), and there is no way to test PostgreSQL behavior in this environment without database credentials (Docker off, no local `psql`).
- **Decision**:
  1. **Identity moves to JDBC; other domains stay in-memory until their phase.** `organizations`, `users`, `organization_memberships` and `refresh_tokens` are served by `OrganizationRepository`, `IdentityRepository` and `RefreshTokenRepository` (plain SQL over V1 + V3 + V8, ADR-009). Fixed seed UUIDs (`SeedIds`) are shared with the remaining in-memory domains in `DataStore` and with tests, so tenant ids line up across both persistence worlds. `DemoDataSeeder` (an `ApplicationRunner`) inserts 3 organizations / 5 users / 6 memberships idempotently (`ON CONFLICT DO NOTHING`) **only** when `carbonflow.seed.demo-data=true` (default `false` — no demo credential is ever written without explicit opt-in, Phase 1 finding R11 against Node's unconditional production seeding). Passwords are BCrypt cost-10 hashes.
  2. **Refresh rotation with family semantics.** Port of Node's `rotateRefreshToken`: `SELECT … FOR UPDATE` inside the transaction, single-use opaque 64-hex token, 7-day TTL, only the HMAC-SHA256 hash stored (`carbonflow.auth.refresh-secret` from `CARBONFLOW_REFRESH_TOKEN_SECRET`, fail-fast at ≥32 bytes, mirroring the JWT secret), atomic insert-replacement + mark-rotated pair. **Deliberate fix**: replay of an already-rotated token revokes the *entire family* — a thief and the victim both lose the session (Node leaves the legit replacement usable). Rejection paths (expiry, deactivated user, invalid membership, replay) **persist their revocation before answering** (`@Transactional(noRollbackFor = AuthException.class)` mirrors Node's autocommit-per-statement behavior; genuine persistence failures still roll back and answer `AUTH_PERSISTENCE_UNAVAILABLE`).
  3. **Registration → approval lifecycle.** V8 adds `organizations.status` (`PENDING_ACTIVATION`/`ACTIVE`/`REJECTED`/`SUSPENDED` + actor/time/note columns). Public `POST /api/v1/auth/register` (greenfield — no Node counterpart) creates organization (PENDING) + COMPANY_ADMIN user + membership in one transaction and answers **201 without tokens**; sign-in stays blocked until approval. Duplicate email → 409 `EMAIL_ALREADY_REGISTERED` (deliberate tradeoff: a public registration flow cannot avoid confirming an existing email). Authentication requires `ACTIVE`: login → 403 `ORGANIZATION_NOT_ACTIVE` with per-status messages; refresh → 401 `REFRESH_MEMBERSHIP_INVALID` (token revoked). Platform endpoints `GET /api/v1/platform/tenants` + `/{id}/approve|reject|suspend` (gated `platform.tenants.read`/`platform.tenants.manage`, ADR-011) perform the transitions and record actor/time/note.
  4. **Platform organization + PLATFORM_ADMIN seed.** Node's production login requires ≥1 active membership, and no seeded user held `platform.tenants.*` before — the permission existed but was unreachable. A `CarbonFlow Platform` organization plus `platform.admin@carbonflow.test` (role `PLATFORM_ADMIN`) make the platform endpoints and `GET /api/v1/test-suite/run` reachable. `PLATFORM_ADMIN` memberships are excluded from switch/`me` membership options, cannot be assigned by tenant administrators, and the platform organization cannot be selected through tenant switching.
  5. **DB-backed request filter (Node production semantics).** `JwtAuthenticationFilter` re-validates every request against PostgreSQL: user exists + active, active membership in the token's organization — answering Node's exact codes (`INVALID_TOKEN` 401, `USER_DEACTIVATED` 401, `TENANT_ACCESS_DENIED` 403, `AUTH_PERSISTENCE_UNAVAILABLE` 503) instead of a generic 401; a *missing* token still falls through to the entry point (`UNAUTHORIZED`, Node's message). Organization lifecycle status gates token **issuance**, not each request — an already-issued access token lives at most its 15 minutes after a suspension (ADR-010 lifetimes unchanged). `facilityScopes` was dropped from `TenantContext`: nothing consumed it and V1 has no scope column (revisit if facility-level permissions are ever specified).
  6. **Hermetic test database.** `io.zonky.test:embedded-postgres` (test scope only) + a `dbtest` profile: Flyway V1…V8 and the identity seeds run on every `mvn verify` with no Docker or credentials. The JDBC URL carries `stringtype=unspecified` (production and tests): PgJDBC must bind `String` ids as `unknown` so PostgreSQL can infer `uuid` columns — without it every id insert fails with *column "id" is of type uuid but expression is of type character varying*.
- **Documented contract deviations** (all asserted by tests):
  - Blank login fields answer **400 `VALIDATION_ERROR`** (bean validation fires first) where Node answers 401 `INVALID_CREDENTIALS`.
  - Replay of a rotated refresh token revokes the family (stronger than Node, see 2.).
  - The 403 message is generic (*"Insufficient permissions for this operation."*) — Spring does not hand the failing expression to the `AccessDeniedHandler`; code and status match Node.
  - `PUT /organizations/current` validates `consolidationApproach`/`baseYear` → 400 instead of surfacing the V1 CHECK violation as a 500.
  - `POST /auth/refresh` and `/auth/logout` are public routes: the refresh token in the body is the credential (Node parity).
  - Access tokens are stateless: a pre-rotation token survives until its own 15-minute expiry (identical to Node; only the refresh flow revokes).
  - `users.disable` flips the global `users.is_active` flag (per-organization membership removal needs a dedicated endpoint, deferred).
- **Consequences**: All Phase 3 auth flows — login, `/me`, refresh rotation with replay-kill, logout family revocation, tenant/role switching, registration → platform approval → activation, tenant user administration — are implemented in Java against PostgreSQL and covered by 84 tests (embedded PG runs migrations + seeds every build). The platform permission (`platform.tenants.manage`) is now reachable end-to-end. Live-database verification completed 2026-09-26: the application migrated the real `carbonflow_dev` on PostgreSQL 18.6 to v8 (ADR-012 baseline at 6) and served `/api/health` UP against it; the suite itself keeps using embedded PostgreSQL 14.10 hermetically (version difference documented, not a gap for migration correctness). Carried forward: DB TLS and login lockout remain Phase 9 scope, and Node's identity paths are frozen reference only (never modified).

## ADR-015: Scope & Structure — JDBC Scope Domain, Frozen-Matrix Permission Mapping, Server-Persisted Boundaries
- **Status**: ACCEPTED (Phase 4).
- **Context**: Phase 4 implements the organizational scope domain (legal entities, facilities, departments, reporting periods, organizational boundaries + boundary facilities) and the scope-aware authorization foundation. Inspection-first: V1 already defines all six tables (V4 adds per-tenant facility-code uniqueness + ownership range; V5 adds tenant composite indexes), so no migration was required. The Node backend implements only `GET/POST /facilities`, `GET /legal-entities` and `GET/POST /reporting-periods`; `docs/API.md` §2.2 additionally specifies `POST /legal-entities` and `GET/POST /boundaries` that Node never built; departments, boundary membership and all get/update/delete verbs are greenfield. The RBAC matrix is frozen (9 roles / 44 codes / 176 assignments) yet several Phase 4 resources have no dedicated permission codes.
- **Decision**:
  1. **No V9 migration — the schema already carries every constraint Phase 4 needs.** Deletion safety was inspected per foreign-key relationship and is documented in code: facility delete is blocked by `activity_data`/`emission_records` `ON DELETE RESTRICT` (→ 409 `RESOURCE_IN_USE`); department delete is `SET NULL`-safe (`activity_data.department_id`); legal-entity delete unlinks facilities (`ON DELETE SET NULL`); boundary delete cascades `boundary_facilities`. No column was invented — scope tables have **no status/active column**, so lifecycle is delete-only (no soft-delete flag fabricated), and `boundary_facilities` keeps its V1 shape (no `organization_id` added).
  2. **Permission mapping inside the frozen 44-code matrix**: legal entities → `organization.read` / `organization.update` (the codes API.md already assigns); departments → `facilities.*` (sub-facility resources — V1 `facility_id NOT NULL`); boundaries → `reporting_periods.read` / `reporting_periods.update` (a boundary always belongs to exactly one reporting period — V1 `reporting_period_id NOT NULL`); facilities and reporting periods use their own dedicated codes including `facilities.delete` (COMPANY_ADMIN only). The resulting role sets are identical to facility/period management, and no new codes were added.
  3. **Boundary semantics = resource-CRUD over `organizational_boundaries`.** `POST /boundaries` creates a row (201), `PUT` partially updates approach/notes, `DELETE` removes it (membership cascades), membership persists via `POST/DELETE /{id}/facilities`. Membership rows are written only after tenant resolution of both sides **and** a SQL join enforcing `facilities.organization_id = boundaries.organization_id`; the V1 composite primary key makes duplicates impossible (409 `DUPLICATE_BOUNDARY_FACILITY`); all multi-statement writes are `@Transactional`, so a rejected pairing persists nothing.
  4. **Scope-aware authorization foundation (`ScopeService`).** `requireFacility/requireDepartment/requireLegalEntity/requireReportingPeriod/requireBoundary` is the single choke point where client-supplied ids resolve against the caller's organization; every repository statement additionally carries `organization_id = ?`. Missing, malformed (non-UUID ids never reach SQL — no cast-error leak) and cross-tenant ids are indistinguishable: **404 `*_NOT_FOUND`** with "*does not exist or access denied.*" (Phase 3's `USER_NOT_FOUND` pattern generalized). RBAC gates the verb, scope gates the row; later phases (activity data, evidence, audits) reuse the same choke point.
  5. **Validation ported from Node where Node exists**, schema limits validated up front so a VARCHAR overflow can never surface as a 503: facility required-field message, `DUPLICATE_FACILITY_CODE` (409, V4 per-tenant unique index), `INVALID_DATE_RANGE` for inverted periods, Node's required-field messages for period creation. Business rules inspected before enforcing: overlapping reporting periods are deliberately **not** restricted (no rule in schema/Node/docs), and any V1-valid `status` value is accepted (no transition graph is evidenced until the audit-workflow phase). There is no `DELETE /reporting-periods/:id` (405): the frozen matrix has no `reporting_periods.delete` code.
  6. **Phase 2 mock retired for these domains.** `FacilityController` now reads PostgreSQL (201 on create, Node contract payload); `DataStore` keeps its prototype facility/period copies **only** as fixtures for the not-yet-migrated analytics/reports/test-suite mocks, which die when those modules migrate.
- **Documented contract deviations** (all asserted by tests):
  - Missing `facilityType` defaults to `MANUFACTURING` (schema default, Node dev path) — Node's *production* path contains a typo'd default (`MANUFESTURING`) that rejects the omission.
  - Facility responses include `updatedAt` (schema-backed; Node's SELECT omits the column) — additive, non-breaking.
  - Cross-tenant/unknown write references answer **404 `*_NOT_FOUND`** (e.g. `LEGAL_ENTITY_NOT_FOUND`) where Node's production path would accept a foreign `legalEntityId` (it never checked tenancy) or map an FK violation to 400 `INVALID_FACILITY_RELATIONSHIP`; Java pre-validates tenancy and keeps the Node FK mapping as defense-in-depth only.
  - Inverted period ranges answer `INVALID_DATE_RANGE` (Node dev-path message); Node's production path answers `VALIDATION_ERROR` for the same condition. Unparseable dates answer `VALIDATION_ERROR` "Reporting period data is invalid." (Node production message).
  - Legal-entity create/update, departments, boundary verbs and every get/update/delete verb are greenfield (specified by API.md §2.2 or the schema; Node never implemented them).
- **Consequences**: All five scope modules run against PostgreSQL with tenant predicates on every statement, and the prototype `DataStore` no longer serves any Phase 4 endpoint. 48 new tests cover per-module CRUD/validation/RBAC plus explicit IDOR rejections (valid UUIDs from both tenants), the CRITICAL boundary-facility rule (cross-tenant attach rejected with nothing persisted, verified directly against `boundary_facilities`), and the scope allow/deny matrix (facility, department, period, legal entity, boundary). Full suite: 132 tests; `mvn clean verify`, `npx tsc --noEmit`, `npm test` all green. Carried forward: analytics/reports/activity/evidence/audit/calculation endpoints remain prototype-mocked for their later phases.

## ADR-016: Governance & Audit — Ten-State Audit Machine, Review Desk, Evidence Vault, Governed Lock
- **Status**: ACCEPTED (Phase 5).
- **Context**: Phase 5 builds the carbon-audit governance surface. Inspection-first: V1 already defines the nine governance/evidence tables (`carbon_audits`, `audit_checklist_items`, `review_findings`, `review_comments`, `correction_requests`, `audit_approvals`, `audit_lock_events`, `evidence_records`, `evidence_versions`, `evidence_links`) and V7 already widens `carbon_audits.status` to the canonical 10-state CHECK — no migration was needed, so no V9 exists. Node's reference is split: `server/routes.ts` implements transitions, findings, comments and evidence with exact messages, but its `/audit-rooms` model is a 6-state legacy that contradicts the canonical machine, and API.md §2.6/§2.7 specified endpoints Node never built. The frozen RBAC matrix (9 roles / 44 codes) already carries `audits.*` and `evidence.*` — nothing was invented.
- **Decision**:
  1. **One state machine; the legacy model is deleted.** `AuditStateMachine` is the single source for the 10-state graph: `DRAFT→SUBMITTED→DATA_COLLECTION→VALIDATION→REVIEW→(APPROVED|CORRECTION_REQUESTED|REJECTED)` with both resume edges to `DATA_COLLECTION`, then `APPROVED→AUDIT_READY→LOCKED` (terminal) — 11 edges total. The prototype's `AuditRoom`/`AuditStatus` enum and `DataStore.auditRooms` were removed so a second model cannot drift, and `TestSuiteController`'s workflow check now evaluates `AuditStateMachine.isAllowed`. Every edge carries a frozen-matrix permission (submit-class and both resume edges → `audits.submit`; reviewer outcomes → `audits.review`; `REVIEW→APPROVED` → `audits.approve`; readiness + lock → `audits.lock`); everything else is rejected with Node's exact strings ("Cannot transition audit from 'X' to 'Y'. Valid targets: A, B." / "Your role cannot perform the 'X -> Y' transition.").
  2. **Server-side gates, exactly the documented ones.** Unsatisfied mandatory checklist items block `APPROVED`/`AUDIT_READY`/`LOCKED` (400 `CHECKLIST_INCOMPLETE` listing the codes); zero unresolved `HIGH`/`CRITICAL` findings gates the same edges; `CORRECTION_REQUESTED` requires ≥ 1 non-dismissed finding (400 `NO_REVIEW_FINDING`); `REJECTED` requires a reason; every governed write on a `LOCKED` audit answers 409 `AUDIT_LOCKED`. Create seeds the 8 canonical checklist items (`CHK-BND-01`…`CHK-FIN-08`); a duplicate period answers 409 `AUDIT_ALREADY_EXISTS`; draft metadata is updatable only in `DRAFT` (409 `AUDIT_NOT_DRAFT`) and status is never client-settable.
  3. **Review desk over the child tables.** Findings, comments, corrections and approvals resolve their parent audit through `ScopeService.requireAudit`, and every child statement re-joins `carbon_audits` (IDOR defense in depth); child ids pass `requireUuid` first, so malformed == unknown == cross-tenant (404 `*_NOT_FOUND`; `FINDING_NOT_FOUND` matches Node `routes.ts:929`). Comments are author-edit/author-delete only (403 `NOT_COMMENT_AUTHOR`); correction requests are windowed to `REVIEW`/`CORRECTION_REQUESTED` (409 `AUDIT_NOT_IN_CORRECTION_WINDOW`) and always name a tenant-owned `activity_data_id`. Approvals are read-only from the client (`GET` only; `POST`/`PUT` → 405) — rows are written solely by the `REVIEW→APPROVED` transition, which stamps a SHA-256 signature hash over `auditId|approverId|role|REVIEW->APPROVED`.
  4. **Evidence vault = Node's chain, structurally safer.** Upload validates in Node's order — `FILE_MISSING` → optional `entityType`/`entityId` relationship pre-check (uniform 400 `INVALID_EVIDENCE_RELATIONSHIP` for malformed/unknown/foreign targets, no existence oracle) → 25 MB → MIME allow-list → magic bytes → SHA-256 — then writes the record + `evidence_versions` v1 with best-effort file cleanup if any step fails; multipart caps are 25/28 MB (over-limit parts → 400 `UPLOAD_FAILED`). Versioning appends rows and repoints the record to the head; download serves the head with CR/LF/quote-sanitized filenames; delete cascades rows and files but answers 409 `EVIDENCE_IN_USE` while audit-linked (duplicate links → 409 `DUPLICATE_EVIDENCE_LINK`). `storagePath` is `@JsonIgnore` on field and getter; storage stays local (`vault_storage/`, `carbonflow.evidence.vault-dir`) — no cloud and no encryption-at-rest claims.
  5. **Governed lock, honestly named.** `LOCKED` runs one transaction: SHA-256 `governanceStateHash` over `auditId|periodId|LOCKED|checklist[…]|findings[…]`, an `audit_lock_events` row, and the reporting-period freeze via `ReportingPeriodRepository.updateStatus`. The claim is **GOVERNED AUDIT LOCK** — an integrity checksum over frozen rows the application refuses to write — not cryptographic immutability (Javadoc, API.md §2.6 and AUDIT_WORKFLOW.md all say so).
  6. **List/detail parity, additive where Node is silent.** Both views carry `checklistSummary{total,satisfied}` and `openFindingsCount` (Node enriches only the list route); detail additionally exposes `corrections`, `approvals` and `lockEvent`. No Node field was renamed or removed.
- **Documented contract deviations** (all asserted by tests):
  - A present-but-empty upload part answers 400 `FILE_MISSING` (Node's handler had no zero-byte check), and checklist verify requires an explicit `isSatisfied` (Node coerced an absent value to `false`).
  - `title` ≤ 255, `code` ≤ 50 and `fileName` ≤ 255 are validated up front → 400 instead of surfacing a V1 VARCHAR overflow as 503.
  - Comment creation is gated `audits.review` (Node left comment creation ungated; API.md §2.6 always specified the permission).
  - Evidence 404s answer Node's exact code *and* message (`EVIDENCE_NOT_FOUND`, "Evidence document not found or cross-tenant access prohibited.") for malformed as well as foreign ids — the label-derived `EVIDENCE_DOCUMENT_NOT_FOUND` was deliberately avoided so a malformed id cannot be distinguished from a missing one.
  - Audit 404 messages use the Phase 3/4 shape ("Audit does not exist or access denied.") where Node's own two handlers disagree with each other ("Audit not found." vs "Audit record not found."); code and status are identical.
  - Correction requests (list/create/resolve-flag) are greenfield — Node has no endpoint — and use `isResolved` JSON naming consistent with the checklist's `isMandatory`/`isSatisfied` (Java bean naming would otherwise strip the `is`).
  - The canonical workflow document's role column expresses intent; where the frozen matrix differs (CAcc holds no `audits.submit`; AP may also reject; CA may also approve; SM may also lock), the permission is authoritative — documented in AUDIT_WORKFLOW.md's enforcement note.
- **Consequences**: All Phase 5 surfaces run against PostgreSQL with tenant predicates on every statement and a single state model. 44 new tests (176 total) cover the exhaustive 10×10 transition matrix with Node byte-for-byte rejection messages, per-edge permissions, lifecycle + gates, checklist CRUD/verify, findings/comments/corrections/approvals including RBAC and item-level IDOR, the evidence validation chain/versioning/links/delete with IDOR across every verb, and the governed lock (frozen comments, 409 matrix, period freeze, hash/signature rows). Full battery green: `mvn clean verify` (176 tests), `npx tsc --noEmit`, `npm test`. No V9 was created. Carried forward: activity-data/inventory domain convergence and `/factors` legacy (Phases 6–7); login lockout and DB TLS (Phase 9); Node remains frozen reference only.

## ADR-017: Carbon Accounting Core — Deterministic Engine, Emission Ledger, Scope 2 Dual Reporting, Audit-Aware Writes
- **Status**: ACCEPTED (Phase 6).
- **Context**: Phase 6 delivers the canonical carbon flow — activity data→validation→factor selection→unit normalization→calculation→gas-level results→emission records→provenance/snapshot. Inspection-first: V1–V8 already contain the complete accounting schema (`activity_data`, `emission_factors`, `emission_factor_versions`, `gwp_sets`, `gwp_values`, `calculation_methodologies`, `calculations`, `calculation_gas_results`, `emission_records`) — no migration was needed, so **no V9 exists**. Node's `server/calc.ts` + `server/calculation-repository.ts` carry the reference behavior with exact messages, but the Node server stays frozen (read-only parity oracle), while API.md §2.3–§2.5 specified endpoints Node never built. The frozen RBAC matrix already carries `activity_data.*`, `calculations.*`, `reports.read` and `emission_factors.read` — nothing was invented.
- **Decision**:
  1. **One accounting model; the in-memory duplicate is deleted.** PostgreSQL is the only ledger. `DataStore`'s calculation/emission/factor/GWP maps were removed so a second model cannot drift (facilities, reporting periods, evidence and audit-trail caches remain for their own modules), and the unused `EmissionCategory` enum was dropped. Every statement is tenant-predicated and the organization always comes from `TenantContext` — a client-supplied organization id is never read.
  2. **Deterministic engine, exact arithmetic.** `GhgCalculationEngine` is pure `BigDecimal` (precision 28, HALF_UP): per gas `raw_kg = normalized × gasFactor`, `co2e_kg = raw_kg × GWP`, gas rows in engine order CO2/CH4/N2O; composite factors (refrigerants, green tariffs) bypass GWP; totals accumulate unrounded products and round only at presentation. Unit normalization goes through the exact conversion table (`UnitConversionService`): same-unit identity returns 1, an unknown pair is a hard error. The output carries `SHA-256(activityId|factorVersionId|gwpSetId|plain(normalized)|plain(tonnes))` — an integrity checksum for engine determinism, not a cryptographic seal.
  3. **Provenance is the snapshot; history cannot drift.** Every calculation persists original + normalized quantity and units, conversion factor, factor id/version/value/unit/source/year, GWP set id and name, gas results and timestamp. References are resolved *before* the write (active factor version for the activity type, platform-default or explicitly requested GWP set — no hardcoded GWP fallbacks), and `CalculationPersistence` re-reads them inside the transaction and compares them with the snapshot; a mismatch aborts with the same wire code the reference surface uses (`503 CALCULATION_PERSISTENCE_UNAVAILABLE`) instead of writing a hybrid. A later active factor version can only supersede `emission_records` rows — it can never edit a `calculations` row.
  4. **One transactional writer; independent batch.** `CalculationPersistence` is the only `@Transactional` bean: pre-write tenant assertions→`SELECT ... FOR SHARE` on the activity with an anchor re-check→gas rows + calculation + emission record + supersession of the prior active record + activity `CALCULATED`, all in one transaction. A `23503`/integrity violation maps to `400 INVALID_CALCULATION_RELATIONSHIP` with full rollback — so re-executing an identical calculation trips the deterministic hash, rolls back entirely and leaves the ledger unchanged (asserted by test). Run reads everything outside the transaction and only persists inside; batch runs one transaction per activity with Node's exact split — skips `FACTOR_NOT_FOUND`, `GWP_SET_NOT_FOUND`, `AUDIT_LOCKED`, frozen periods and unsupported units; aborts on relationship errors (Node's singular batch wording, `routes.ts:721`) and contract errors (`400 VALIDATION_ERROR`, "Batch calculation input is invalid.").
  5. **Scope 2 stays split, always.** `LOCATION_BASED` and `MARKET_BASED` are separate `emission_records` rows keyed by `scope2_type`; DUAL_REPORTING retains both, there is no fallback and no location+market sum anywhere. The ledger summary reports five 4-decimal HALF_UP totals (`scope1Tonnes`, `scope2LocationTonnes`, `scope2MarketTonnes`, `totalLocationBasedTonnes`, `totalMarketBasedTonnes`); records without a classification are excluded from Scope 2 sums. `GET /emissions` returns records + summary; `GET /calculations/:id` exposes the snapshot (Node implemented `getCalculation` but never routed it); deliberately **no** `GET /calculations` list and **no** `GET /emissions/:id`.
  6. **Phase 5's governed lock binds accounting.** `AccountingLockGuard` checks the freeze through the existing Phase 4/5 tenant-predicated reads — no Phase 5 code changed. Activity create/update/submit and `calculations/run` answer `409 AUDIT_LOCKED` for a frozen period; batch reports those activities as unprocessed; reads stay open.
  7. **Wire contract = Node's, serialized as numbers.** Decimal fields leave as JSON numbers with trailing zeros stripped (`PlainBigDecimalSerializer`); `scope2Type` is omitted for Scope 1 (`NON_NULL`). Greenfield by-id routes (`PUT /activity-data/:id`, `POST /activity-data/:id/submit`, `GET /calculations/:id`) accept only Node-shaped uuids (`UuidContract.isNodeUuid`, mirroring Node's `UUID_PATTERN`: version nibble 1–5, variant 89ab) and collapse malformed input into the anti-enumeration 404 (`ACTIVITY_NOT_FOUND`, "Activity data not found.") — bad input is indistinguishable from missing data. Reference data is read-only: `GET /reference/gwp-sets` is authenticated-only, `GET /reference/emission-factors` and `GET /reference/methodologies` (greenfield) require `emission_factors.read`. The methodology route is additive reference exposure: `calculations` has never had a methodology column (ADR-008 fixed the snapshot and V9 is forbidden), so no calculation claims a methodology it cannot prove.
- **Documented contract deviations** (all asserted by tests):
  - Unsupported unit pairs are never silently multiplied by 1: `run`→`400 Unit conversion from X to kWh is not supported.`, `batch`→skipped (Node's engine falls back to ×1); same-unit identity still returns 1.
  - Timestamps serialize as ISO-8601 (`Instant`) instead of PostgreSQL `::text`.
  - A snapshot/reference mismatch inside the persist transaction surfaces as `503 CALCULATION_PERSISTENCE_UNAVAILABLE` (the reference lets the raw error escape).
  - Activity by-id 404s answer `ACTIVITY_NOT_FOUND` / "Activity data not found." where Phase 5's evidence chain used `ACTIVITY_DATA_NOT_FOUND` — both texts exist in Node; each route keeps its own code.
  - Quantity parsing is bounded up front (non-negative, scale ≤4, ≤12 integer digits, explicit `null` rejected)→400 `VALIDATION_ERROR` instead of a database numeric overflow surfacing as 503. Create accepts only an absent status or `SUBMITTED`; PUT only `DRAFT|SUBMITTED|VALIDATED` (engine-owned `CALCULATED`/`LOCKED` rejected); tenant anchors are immutable.
  - `GET /activity-data` invalid filters answer `400 VALIDATION_ERROR` with Node's production catch-all text ("Activity persistence is temporarily unavailable.") — byte-identical to the distinct `503 ACTIVITY_PERSISTENCE_UNAVAILABLE` body, distinguishable only by code/status.
  - 403s carry the generic "Insufficient permissions for this operation." where Node sometimes varies the text per role — the frozen permission matrix decides, not the wording.
  - Batch skips frozen-period activities and unsupported units (Node has no lock concept and normalizes by 1); `run` enforces the Phase 5 lock that Node's accounting routes never checked; create/update/submit enforce it too.
  - Scope 2 classification is enforced at insert and asserted DB-wide by the platform self-test — the reference has no such invariant.
- **Consequences**: 34 new tests (210 total) cover the activity CRUD/validation contract, the run error matrix, batch skip/abort semantics, Scope 2 side-by-side arithmetic proving LOCATION ≠ MARKET, ledger/supersession/summary rules, the Phase 5 lock interaction (409 `AUDIT_LOCKED` on every accounting write, reads open), reference-data parity and the unit-conversion table; the platform self-test suite runs 7/7 green against PostgreSQL. Full battery green: `mvn clean verify` (210 tests), `npx tsc --noEmit`, `npm test`. No V9 was created and `src/services/api.ts` is unchanged (the frontend already targets these paths). Carried forward: dashboards/analytics features/targets, frontend redesign, deployment, Node decommission, `POST /reference/emission-factors` and `/data-requests` (documented API gaps), login lockout and DB TLS (Phase 9).
